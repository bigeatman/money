# OpenDART 기업자료 수집·변경분 캐시

OpenDART API 호출, 원문 보관, 변경 비교와 재무비율 계산을 Python이 수행합니다. 이 과정에서 LLM을 호출하지 않습니다. Work에는 저장된 요약·변경 목록을 먼저 전달하고, 필요한 근거만 페이지로 읽게 합니다.

## 이번 구현 범위

| 자료 | 수집·보관 방식 |
| --- | --- |
| 기업 목록 | `corpCode.xml`에서 종목코드가 있는 발행기업 전체. 하루마다 갱신하며 신규 기업을 추가하고 목록에서 사라진 기업의 과거 자료도 보존합니다. |
| 기업 개황 | `company.json`. 신규 기업 또는 기업코드 목록의 수정일이 바뀐 기업을 조회합니다. 결산월 등 원래 값을 보존합니다. |
| 공시 목록 | `list.json`의 유가증권·코스닥·코넥스 구분을 모두 조회합니다. 7일 단위 구간에서 모든 페이지를 읽고 정정 이전 공시도 포함합니다. |
| 공시 원문 | 발견한 공시와 재무제표 응답의 접수번호로 `document.xml`을 받아 ZIP 원본을 압축 보관합니다. 검색용 텍스트는 원본으로부터 생성합니다. |
| 재무제표 | `fnlttSinglAcntAll.json`의 전체 계정. 기본 당해연도와 이전 2개년, 사업·1분기·반기·3분기, 연결(CFS)·별도(OFS)를 각각 보관합니다. |
| 계산값 | 표준 계정이 하나로 확인되고 통화가 일치할 때만 영업이익률·부채/자본 비율·유동비율을 계산합니다. 계산에 쓴 금액·통화·기간·계정 ID·접수번호를 함께 반환합니다. |
| 이력 | 원본 버전, 필드별 변경 전후 값, 공시 텍스트 차이, 수집 시각, 작업 큐와 오류, 요청 사용량을 보존합니다. |

대상은 **OpenDART 기업코드 목록의 상장 발행기업**입니다. KRX 모든 증권·우선주·ETF·ETN의 개별 종목 목록과 같지 않습니다. 미국 기업, 시세, 경제지표, 신용평가사의 유료 보고서, 증권사 리서치와 투자판단 항목 전체를 이 수집기 하나로 확보하지 않습니다. 기존 시세 수집기와 ETF/ETN 정책은 그대로 둡니다. 매수·매도 판단이나 주문도 수행하지 않습니다.

`status=complete`는 설정 범위에서 API 작업을 처리했다는 뜻입니다. `no_data`와 `document_unavailable`도 구분해 포함하므로, 이것이 모든 자료의 존재 또는 투자 검토 완료를 뜻하지 않습니다. `coverage.investment_review_complete`는 항상 `false`입니다.

## 기존 설치에 적용하고 키 입력

소스를 반영한 뒤 기존 설치의 `코드` 디렉터리에서 실행합니다. 기존 `config.json`에 `opendart` 항목이 없어도 기본값을 사용합니다. 기존 설정이나 주문 장부를 초기화할 필요가 없습니다.

```bash
python -m money.cli dart-credentials
python -m money.cli dart-sync
python -m money.cli dart-status
```

첫 명령에서 OpenDART 인증키를 화면에 표시하지 않고 입력합니다. 키는 해당 설치의 `.env` 안 `OPENDART_API_KEY`에만 저장하며 파일 권한은 `600`입니다. 실행 중인 데몬은 키 입력 후 재시작해야 읽습니다. 키를 GitHub·채팅·명령행 인자에 붙이지 않습니다. 새 설치에서만 먼저 `python -m money.cli init`을 실행합니다.

`dart-sync`는 주문 장부나 증권사에 접근하지 않으므로 데몬을 중지하지 않고 실행할 수 있습니다. 동일 DB에 수집기가 이미 있으면 `already_running`을 반환합니다. 키가 없으면 `missing_key`로 일시 중지하며 네트워크 요청을 보내지 않습니다.

데몬의 `run` 루프는 키가 있고 `enabled=true`이면 기본 1시간마다 백그라운드 수집을 시작합니다. 프로그램이 실행 중일 때의 주기이며, 별도 ChatGPT 예약을 만들거나 AI 분석을 실행하지 않습니다.

## 최초 구축과 다음 회차

1. 최초에는 전체 기업 목록, 기본 365일 공시와 모든 설정 재무제표 슬롯을 수집합니다. 종목 수·후보 수로 임의 절단하지 않습니다. 기업당 기본 24개 재무제표 요청에 개황·원문 요청이 더해지므로 한 회차나 하루 안에 끝나지 않을 수 있습니다.
2. 회차당 기본 1,000회, 한국 날짜 기준 하루 18,000회의 로컬 요청 예산을 적용합니다. HTTP 재시도도 횟수에 포함합니다. 한도 또는 API의 제한 응답으로 멈추면 다음 실행에서 큐와 공시 조회 구간을 이어갑니다. 실제 발급키 한도와 다른 프로그램의 사용량은 별도로 적용됩니다.
3. 이후에는 마지막 완료한 공시 날짜에서 기본 2일을 겹쳐 조회합니다. 날짜가 바뀌어도 겹침을 적용합니다. 장기간 미실행한 경우 최초 365일 제한으로 공백을 잘라내지 않고 마지막 완료 지점 이후를 모두 따라갑니다.
4. 새 공시·공시 메타데이터 변경만 저장하고 원문 작업을 추가합니다. 사업·분기·반기·감사보고서가 발견되면 **해당 기업의 설정 기간 재무제표만** 다시 확인합니다. 일반 계약 등 비재무 공시만으로 전체 재무제표를 다시 요청하지 않습니다. 기업 개황은 기업 목록의 수정일 변경으로 갱신합니다.
5. 원문 ZIP의 시간·파일 순서와 재무제표 행 순서·응답 메시지는 데이터 변경에서 제외합니다. 같은 내용이면 새 변경 이벤트를 만들지 않습니다. 변경 전 버전은 삭제하지 않습니다.
6. 전송 실패는 `no_data`로 바꾸지 않습니다. 미완료 큐로 두고 다음 시간에 재시도합니다. 원문 미제공(`013`/`014`)은 명시해 보관하고 하루 뒤 재확인합니다. 재무제표 `013`은 금액 0이 아니라 해당 요청의 API 자료 없음이며, 새 관련 공시가 나오면 다시 확인합니다.

12월 결산 기업은 공시명에 표시된 회계기간과 최신 관련 접수번호를 대조합니다. 정정공시가 있는데 재무 API가 예전 접수번호를 반환하면 `financial_api_lag`로 남기고 이전 값을 `stale=true`로 제공합니다. 다른 결산월은 자동 기간 대응을 단정하지 않고 원래 기간 표기와 경고를 제공합니다.

재무제표 `thstrm_amount`의 손익 항목은 연간 또는 해당 3개월 값입니다. 누적값 `thstrm_add_amount` 등 원래 필드도 원본에 남깁니다. 연결·별도를 합산하지 않으며 계정이 모호하거나 통화·금액이 없으면 비율을 생략합니다.

## 한 파일 기준점과 백업

운영 DB는 `runtime/fundamentals.sqlite`입니다. 증권 주문 장부 `runtime/state.sqlite`와 분리되어 있습니다. 수집 도중에는 SQLite의 WAL 보조 파일이 생길 수 있으므로 운영 DB만 임의 복사하면 최신 자료가 빠질 수 있습니다. 다음 명령으로 WAL까지 반영한 **단독 SQLite 파일**을 생성합니다.

```bash
python -m money.cli dart-export --file /원하는/경로/fundamentals-baseline.sqlite
```

기존 파일을 덮어쓰지 않습니다. 내보낸 한 파일에 기업·공시·개황·재무제표·압축 원문·변경 이력·재개 정보가 모두 들어가며 인증키는 들어가지 않습니다. SQLite로 직접 읽을 수 있습니다. 복원할 때는 수집기를 모두 중지하고 기존 DB와 WAL을 함께 보관한 뒤 스냅샷을 별도 실행 루트에 배치합니다. 주문 장부는 교체하지 않습니다.

스키마는 `PRAGMA user_version=1`입니다. 지원하지 않는 스키마는 삭제하거나 초기화하지 않고 거부합니다. 향후 형식 변경에는 별도 마이그레이션이 필요합니다. 현재 비율과 원문 텍스트는 저장된 원본에서 계산하므로 그 계산 코드 변경만으로 원문을 다시 다운로드하지 않습니다. `history_years`를 늘리면 다음 동기화에서 빠진 기간 작업이 추가됩니다. `disclosure_days`는 최초 공시 구축 범위이며, 이미 만든 DB의 과거 공시 범위를 늘리는 명령은 이번 버전에 포함하지 않습니다.

## CLI 조회

```bash
python -m money.cli dart-show --limit 100
python -m money.cli dart-show --symbol 005930 --limit 100
python -m money.cli dart-show --after-seq 120 --limit 20
```

기본 조회는 기업 목록, `--symbol`은 그 기업의 재무제표 요약, `--after-seq`는 저장된 순번 이후의 변경 목록입니다. `next_offset` 또는 `next_after_seq`를 따라 끝까지 읽습니다. `collected`는 현재 내용 버전을 저장한 시각이며, 내용이 같았던 마지막 API 확인 시각을 뜻하지 않습니다.

## AI에 전달할 MCP 조회

| 도구 | 전달되는 데이터 |
| --- | --- |
| `start_fundamental_sync` | 비동기 수집 시작 또는 이미 실행 중인 상태. 원문 대량 응답 없음. |
| `get_fundamentals` | 기본 기업 목록, `symbol`별 비율·자료 상태, 또는 `after_seq` 이후 변경 요약. 회당 최대 100행. 네트워크 요청 없음. |
| `get_fundamental_evidence` | 위 조회의 `source_key` 또는 `diff_key`에 해당하는 캐시 근거. 기본 4,000자, 최대 8,000자와 다음 위치. 네트워크 요청 없음. |

변경분 검토 절차:

1. 최초 검토에는 `after_seq=0`을 사용합니다. 이후에는 해당 검토자가 마지막으로 **검토를 마친** 순번을 사용합니다.
2. 첫 응답의 `through_seq`를 다음 페이지에도 그대로 넘깁니다. 그 사이 새 수집이 일어나도 한 번의 검토 범위가 고정됩니다. `next_after_seq`를 따라갑니다.
3. 필요한 `diff_key`로 전체 변경 전후 값과 원문 차이를 읽고, 필요한 기업의 `source_key`로 근거를 읽습니다. 긴 근거는 `next_offset`으로 이어갑니다. 공시 원문 링크도 제공합니다.
4. 마지막 페이지의 `completed_through_seq`는 조회가 끝난 범위입니다. 실제 검토와 필요한 근거 확인까지 끝난 경우에만 검토자 측에 저장합니다. API 수집기가 AI 판단의 완료를 대신 기록하지 않습니다. `symbol`로 범위를 좁혔으면 그 기업 전용 커서로 관리하고 전체 기업 검토 커서와 혼용하지 않습니다.

예를 들어 `after_seq=120` 첫 페이지에서 `through_seq=185`, `next_after_seq=140`을 받으면 다음 호출은 `after_seq=140, through_seq=185`입니다. 모든 페이지와 필요한 근거 검토 후 185까지 완료했다고 기록합니다. 다음 회차는 185 이후만 읽습니다. DB를 교체·복원했다면 커서를 재검증해야 합니다. 존재하는 이력보다 앞선 순번이나 역전된 범위는 거부합니다.

공시 텍스트는 외부 근거로 표시합니다. 원문 안 문장을 프로그램 또는 AI에 대한 실행 지시로 취급하지 않습니다. 같은 기업·기간·제출인의 같은 제목을 기준으로 원문을 비교하며, 이것만으로 법적인 원공시-정정공시 관계를 확정했다고 주장하지 않습니다.

## 설정과 검증

`config.example.json`의 `opendart` 설정을 참고합니다. `enabled=false`로 데몬의 자동 수집을 끌 수 있으며 기존 캐시는 계속 조회할 수 있습니다. 요청 속도·회차 예산·일 예산을 발급키 조건에 맞게 조정합니다. 자료가 없는 키도 캐시를 조회·내보낼 수 있습니다.

```bash
python -m unittest discover -s tests -v
```

합성 응답으로 전체 페이지·종목 수집, 연결/별도, 동일 자료 재사용, 정정 비교, API 지연·실패, 한도·중단 후 재개, 다중 수집 방지, 근거 분할 조회와 단일 파일 내보내기를 검사합니다. 실제 인증키 수집과 휴대폰 배포는 이 오프라인 검증에 포함하지 않습니다.
