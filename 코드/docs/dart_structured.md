# 종목 목록 → OpenDART → 가공 → SQLite

기존 `manage_dart_collection` 도구에 `plan.mode="structured"`를 전달한다. MCP 주소와 입력 스키마가 같아서 플러그인을 재생성할 필요가 없다. 휴대폰의 Python 서버는 소스 업데이트 후 재시작해야 한다.

```json
{
  "action": "start",
  "plan": {
    "mode": "structured",
    "symbols": ["005930"],
    "years": [2025],
    "report_codes": ["11013", "11012", "11014", "11011"],
    "fs_divs": ["CFS"],
    "disclosure_from": "20250101",
    "disclosure_to": "20261020",
    "workers": 8,
    "request_interval_seconds": 0.3,
    "refresh": false
  }
}
```

- `symbols` 대신 `companies: [{"symbol":"005930","corp_code":"00126380"}]`를 줄 수 있다. 둘을 함께 쓰지 않는다. 법인코드는 명시값 → 로컬 종목 목록 순서로 확인한다. 목록에 없는 종목은 D0 법인 사전을 한 번 받아 해결하되 선택한 종목만 목록에 넣는다. 이 초기 작업은 `bootstrap_ms`로 분리한다.
- `years`는 사업연도다. `disclosure_from/to`는 D2의 **공시 접수일** 범위이며, 기본값은 지정 사업연도의 첫해 1월 1일~마지막해 12월 31일이다. 예를 들어 2025년 사업보고서가 2026년에 접수될 수 있으므로 필요한 접수일 범위를 별도로 지정한다.
- 보고서 코드는 1분기 `11013`, 반기 `11012`, 3분기 `11014`, 사업보고서 `11011`이다. `fs_divs`는 연결 `CFS`, 별도 `OFS` 중 지정하며 자동 대체하지 않는다.
- 기본 수집은 D1, D2, D4~D14다. D3 원문/주석은 요청하지 않는다. `apis`로 이 범위의 일부만 고를 수도 있다.
- D2는 100건씩 모든 페이지를 받고 건수·페이지·접수번호 중복을 확인한다. D14는 2026년 이후 V2를 먼저 조회하고, 2015~2025년은 기존 스키마를 먼저 조회한다. 자료 없음(013)이면 반대 스키마도 한 번 확인하며 결과를 별도로 보존한다.
- 1개 종목·1개 연도·4개 보고서·연결 기준의 기본 요청은 **46회**다. D2 추가 페이지와 D14 스키마 확인, 처음 필요한 D0는 별도다. 연결+별도면 기본 50회다. 제공기관의 자료 없음도 조회 결과이며 실제 데이터가 있다는 뜻은 아니다.

## 병렬 처리와 저장

`workers`는 전체 목록이 공유하는 동시 수집 작업 수다. 종목 간에 차례를 배분하므로 한 종목이 전체 슬롯을 선점하지 않는다. SQLite WAL을 사용하고 API 응답을 기다리는 동안 쓰기 트랜잭션을 열어 두지 않는다. 원본 보관/색인과 가공 결과는 짧은 트랜잭션으로 커밋한다. SQLite 동시 쓰기는 1개이고 네트워크 요청이 병렬이다.

원본 응답·해시·모든 필드는 기존 아카이브에 보존된다. `structured_rows`에는 원본 행(`provider`)과 명시된 숫자 필드의 Decimal 변환값(`numeric`)을 저장한다. 식별자와 날짜는 숫자로 바꾸지 않는다. 빈 값/대시/비정상 숫자는 NULL이며 0으로 채우지 않는다. `structured_calculations`에는 기존의 명확한 XBRL 계정과 통화가 확인될 때만 매출·영업이익·유동비율 등 고정 계산 결과와 근거를 저장한다. 주식 수는 `istc_totqy - tesstk_co`를 별도 계산한다. 투자 평가나 문서 해석은 수행하지 않는다.

응답마다 가공 행과 요청 성공 상태를 같은 트랜잭션에 넣는다. 전체 종목의 단일 트랜잭션은 아니다. 중단 뒤에는 같은 `job_id`로 재개하여 커밋한 요청을 건너뛴다. 실패한 요청을 재시도하려면 `retry_failed=true`를 명시한다. 인증/할당량 오류는 `paused`, 개별 오류와 페이지 불일치는 `incomplete`이며 성공으로 표시하지 않는다. 입력과 다른 법인·연도·보고서·연결/별도 응답은 가공 저장을 롤백하되 원본 오류 근거는 남긴다.

```json
{"action":"status","job_id":"structured_반환된ID","limit":100}
```

`next_offset`이 있으면 이어서 읽는다. 상태에는 회사별 진행 수와 요청별 `fetch_and_archive_ms`, `normalize_and_commit_ms`, `received_to_commit_ms`가 있다. 실행 결과의 `observed_peak_fetches`는 속도 대기·아카이브 처리를 포함한 실제 동시 수집 작업 수다. `timings_by_symbol.last_response_to_final_commit_ms`는 이번 실행에서 해당 종목의 마지막 응답 바이트를 받은 시점부터 최종 가공 커밋까지다. 캐시만 사용하면 이 값은 NULL이다. 측정값은 현재 재개 실행에 한정한다.

응답당 1초여도 46개 호출이 모두 1초에 끝나는 것은 아니다. `workers=8`이면 여러 차례로 나뉘며, 전역 요청 시작 간격과 재시도도 영향을 준다. `request_interval_seconds=0`으로 시작 간격을 없앨 수 있으나 OpenDART가 반환하는 제한/오류는 그대로 적용한다. 전체 응답이 도착한 뒤의 가공·저장 시간과 총 수집 시간을 구분한다.

## 폰의 병렬 수 확인과 조절

```bash
python -m money.cli dart-capacity
python -m money.cli dart-capacity --benchmark
```

MCP에서도 `{"action":"status"}`로 자원을 조회하고, `{"action":"status","plan":{"mode":"capacity","benchmark":true}}`로 동일한 로컬 성능 진단을 실행한다. 성능 진단은 임시 DB에서 가상 응답을 사용하여 실제 아카이브·가공·커밋 경로를 실행한다. DART 호출은 0회이고 실제 종목 DB에 가상 데이터를 넣지 않는다. 측정한 요약만 저장한다.

소프트웨어 상한은 32이며 CPU 가용 수, 가용 RAM(작업당 128MiB 예산), 파일 디스크립터 여유를 반영해 낮춘다. 기본은 그 범위에서 최대 8이다. 이 자원 예산은 운영상 추정값이며 실제 작업당 메모리 보장이 아니다. `maximum_verified_workers`는 이 기기에서 로컬 시험을 통과하며 관측한 최대 병렬 수다. `fastest_fixture_workers`는 같은 시험에서 가장 빨랐던 설정이다. 실제 DART의 최적값이나 폰의 절대 하드웨어 한계를 뜻하지 않는다. 실제 수집의 지연·오류·처리량을 보고 다음 계획의 `workers`를 조절한다.

## 오프라인 검증

```bash
python -m unittest discover -s tests -v
```

실제 DART 호출 없이 전체 API 범위, 지정 종목 제한, 페이지 누락/변경, 원본/가공 저장, 자료 없음, 할당량 중단/재개, 작업 수 제한, 1초 응답의 병렬 실행을 검증한다. 휴대폰 성능과 실제 제공기관 응답은 업데이트 후 별도로 측정한다.
